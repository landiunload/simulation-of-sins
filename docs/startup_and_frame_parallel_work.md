# Запуск и кадр без vsync: где уходит время

Ветка `peer/startup`, голова `20fffba`. Движок (`../laiue`, `2f2781d`)
только читался. Изменения — в [src/app/application.c](../src/app/application.c),
[src/CMakeLists.txt](../src/CMakeLists.txt) не тронут, новый тест
[tests/cmake/startup_profile_test.cmake](../tests/cmake/startup_profile_test.cmake)
и его регистрация в [tests/CMakeLists.txt](../tests/CMakeLists.txt). Правок
в `game/*.c` нет: измерение не показало лишней работы в коде игры.
Формат `SOS_FRAME_PROFILE` не сломан — новые столбцы только в конец, столбцы
22 (`indexed`) и 23 (`physics_threads`), которые читают
`physics_overrides`/`physics_defaults`, остались на местах.

## 0. Главное

- **Время до первого полностью заполненного куба чанков определяет
  создание рендера, а не стриминг и не контент.** `RendererCreate` —
  медиана **222,6 мс** (210,9…258,3) из **259,6 мс** до заполнения в
  сфокусированном окне, то есть ~86 %. Каталог контента — 0,013 мс,
  `RendererPrepareWorldFrom` — 5,5 мс, всё остальное вместе — доли
  миллисекунды.
- **Заполнение куба — ровно 8 кадров** (125 заявок, 25 непустых мешей,
  бюджет движка `MESH_UPLOADS_PER_FRAME = 4`). В сфокусированном окне эти
  8 кадров стоят ~17 мс; в несфокусированном — 427 мс, потому что движок
  намеренно спит 50 мс на кадр вне фокуса (экономный режим ~20 к/с). Это
  режим окна, а не работа кадра.
- **В кадре без vsync при 4000 телах 95 % — физика** (7,48 мс/тик при
  бюджете 7,8125 мс). Собственная работа игры (инстансы, Draw стриминга,
  `SetCenter`/`Pump`, «между») — **0,86 %**. При 500 телах кадр упирается
  в `present` движка (0,24 мс, 82 %), игра — 3,6 %.
- **Собственной очевидно лишней работы в коде игры измерение не выявило** —
  ни на запуске, ни в кадре. Всё время в вызовах движка; это результат.

## 1. Чем и как измерялось

Две новые переменные окружения (обе по умолчанию выключены, в обычном
прогоне измерений нет):

- `SOS_STARTUP_PROFILE=<путь>` — пишет CSV стадий запуска и закрывает клиент
  на первом кадре, где куб чанков полностью обработан:
  `stage,elapsed_seconds,delta_seconds,queued_chunks,uploaded_meshes,`
  `completed_builds,peak_unfinished,build_avg_ms,frames,bodies`.
  Стадии: `window_create`, `input_create`, `content_catalog`,
  `renderer_create`, `renderer_material_names`, `renderer_prepare_world`,
  `cube_field_init`, `physics_pool`, `cube_mesh_create`, `world_create`,
  `world_populate`, `streaming_create`, `camera_init`, `run_loop_begin`,
  `first_filled`. Время — монотонное `PlatformTimeSeconds`.
- `SOS_NO_VSYNC=1` — `RendererSetVerticalSync(renderer, false)`. Без него
  `present` — это ожидание кадрового импульса (~16 мс), а не работа.

«Полностью заполненный куб» определяется детерминированно через
`ChunkStreamingGetStats`: `queued_requests > 0`,
`queued_requests == completed_builds`, `pending_requests == 0`,
`pending_results == 0` — то есть все 125 заявок куба 5×5×5 построены и
забраны. Из 125 чанков непустых 25 (слой пола z=0), остальные — воздух без
меша; поэтому `uploaded_meshes = 25`.

**Про фокус.** Запуск из скрипта оставляет окно несфокусированным, и
`WindowRunLoop` спит по 50 мс на кадр вне фокуса. Чтобы измерить честную
стоимость кадра, окно активировалось `WScript.Shell.AppActivate` во время
прогона. Профиль кадра (`frame_avg_ms`, `fps`) при этом показывает именно
работу `OnFrame` (от `frameStart` до `frameEnd`), без сна; но настенные
время до заполнения и `fps` сон учитывают. Оба случая ниже разведены.

## 2. Стадии запуска

Windows MSVC Release, x86_64. Медиана (минимум…максимум) по 5
сфокусированным и 7 несфокусированным прогонам, миллисекунды на стадию
(`delta_seconds`):

| стадия | сфокусировано, 5 прогонов | без фокуса, 7 прогонов |

| `input_create` | 0,066 (0,063…0,073) | 0,105 (0,074…0,114) |
| `content_catalog` | **0,013** (0,013…0,019) | 0,024 (0,014…0,026) |
| `renderer_create` | **222,6 (210,9…258,3)** | **239,4 (232,8…256,4)** |
| `renderer_material_names` | 0,040 (0,037…0,058) | 0,040 (0,037…0,046) |
| `renderer_prepare_world` | 5,5 (4,7…6,1) | 4,9 (4,6…5,9) |
| `cube_field_init` | 0,070 (0,069…0,089) | 0,073 (0,065…0,110) |
| `physics_pool` | 0,096 (0,089…0,099) | 0,100 (0,096…0,133) |
| `cube_mesh_create` | 0,387 (0,360…0,468) | 0,424 (0,363…0,560) |
| `world_create` | 0,138 (0,116…0,397) | 0,170 (0,119…0,381) |
| `world_populate` | 0,013 (0,012…0,015) | 0,014 (0,011…0,019) |

Детерминированные счётчики `first_filled` одинаковы во всех прогонах:
`queued_chunks=125`, `uploaded_meshes=25`, `completed_builds=125`,
`peak_unfinished=125`, `build_avg_ms≈0,03`, `frames=8`; `bodies` — просто
число кубов к моменту заполнения (1 в сфокусированном прогоне, ~35 в
несфокусированном, где цикл длиннее). Суммарная работа мешеров:
125 построений × 0,03 мс ≈ 3,8 мс, то есть заполнение ограничено не
построением, а бюджетом загрузки 4 меша на кадр.

## 3. Ответ: что определяет время до первого заполненного кадра

1. **Создание рендера** (`RendererCreate`: устройство D3D12 и swapchain) —
   ~223 мс сфокусировано, ~239 мс без фокуса. Это ~86 % сфокусированного
   времени до первого кадра и не зависит от игры.
2. **Заполнение куба чанков — ровно 8 кадров.** Строительство мешеров
   дешёвое (0,03 мс/чанк), но движок загружает на GPU не больше 4 мешей за
   кадр. Эти 8 кадров стоят ~17 мс, если окно в фокусе, и ~427 мс в
   несфокусированном экономном режиме (50 мс сна на кадр). Стриминг
   «медленный» не по алгоритму, а по числу кадров, и это движковый бюджет.
3. **Контент — 0,013 мс** (`LaiueContentCatalogCreate`) и 5,5 мс
   (`RendererPrepareWorldFrom`: текстурпак, шейдеры, кольца загрузки).
   На общее время не влияют.

Иными словами: контент и игровая обвязка не при чём; время задают движковое
создание рендера и движковый бюджет загрузки мешей за кадр.

## 4. Кадр без vsync

Windows MSVC Release, окно в фокусе, `SOS_NO_VSYNC=1`. Три независимых
прогона по 50 с с общим `SOS_FRAME_PROFILE`; каждая клетка — медиана
(минимум…максимум) по окнам CSV, ближайшим к целевому числу тел. Миллисекунды
на кадр, `physics_tick_avg_ms` — на физический тик.

| метрика | 500 тел | 2000 тел | 4000 тел |
| --- | ---: | ---: | ---: |
| `frame` (вся работа `OnFrame`) | 0,292 (0,260…0,304) | 0,877 (0,621…2,240) | 13,490 (6,180…19,582) |
| `physics` на кадр | 0,027 | 0,405 | 12,869 |
| `physics_tick_avg` | 0,717 (0,647…0,734) | 3,604 (3,576…5,420) | **7,482 (6,802…7,645)** |
| `prepare` (движок: BeginFrame+проходы) | 0,024 | 0,066 | 0,190 |
| `present` (движок, GPU) | 0,239 (0,213…0,250) | 0,405 (0,270…0,624) | 0,427 (0,423…0,639) |
| `streaming` (`SetCenter`+`Pump`) | 0,00024 | 0,00038 | 0,00085 |
| `instances` (`DrawCubes`) | 0,0063 | 0,0371 | 0,1034 |
| `streamdraw` (`ChunkStreamingDraw`) | 0,0031 | 0,0046 | 0,0097 |
| «между» (камера, origin, каркас) | 0,0007 | 0,0010 | 0,0024 |
| `fps` | 3422 (3289…3615) | 1140 (446…1607) | 74 (51…162) |
| **доля игры** (instances+sdraw+stream+between) | **3,6 %** | **4,9 %** | **0,86 %** |

`physics` на кадр при 500 телах мал не потому, что тик дешёвый: кадры идут
~3400 к/с, а тик случается раз в ~30 кадров (аккумулятор). Сам тик —
0,72 мс. При 4000 телах тик стоит 7,48 мс и идёт почти каждый кадр, поэтому
кадр и растягивается до ~13 мс; разброс между прогонами (6…20 мс) — это
шум общей машины, а `physics_tick_avg` устойчив.

Для контроля: тот же клиент с **включённым vsync** даёт `frame ≈ 16,66 мс`,
`present ≈ 14,9…16,6 мс`, `fps ≈ 60` — то есть без `SOS_NO_VSYNC` столбец
`present` измеряет ожидание импульса, как и было в
[frame_cost_parallel_work.md](frame_cost_parallel_work.md).

### Что это значит

- **При 500 телах кадр определяет движковый `present`** (0,24 мс, 82 %);
  игра тратит ~10 мкс. Оптимизировать в игре нечего.
- **При 2000 телах** физика и `present` сопоставимы (0,4 мс каждый), игра —
  ~43 мкс (5 %).
- **При 4000 телах** кадр — это физика (12,9 мс, 95 %), и её тик (7,5 мс)
  почти равен бюджету фиксированного шага 7,8125 мс. Игра — 0,12 мс.
- **Инстансы растут линейно** (6 мкс → 103 мкс на 500 → 4000 тел, ~25 нс на
  тело), `ChunkStreamingDraw` — 3 → 10 мкс, `SetCenter`/`Pump` — доли
  микросекунды. Ни одна из этих частей не является узким местом.

## 5. Что изменено

Игровая логика и симуляция не тронуты. Добавлена только измерительная
обвязка и её тест:

- `application.c`: `SOS_STARTUP_PROFILE` (стадии запуска + `first_filled`),
  `SOS_NO_VSYNC`, разложение кадра на `streaming`/`instances`/`streamdraw`/
  `between` и 8 новых столбцов CSV в конце. Новые измерения вызываются
  только при включённом профиле; в обычном прогоне дополнительных вызовов
  часов нет.
- `tests/cmake/startup_profile_test.cmake` и тест
  `simulation_of_sins.startup_profile`: клиент запускается с
  `SOS_STARTUP_PROFILE`, сам закрывается на заполненном кубе, а тест
  проверяет, что есть стадии и что `first_filled` согласован
  (`queued == builds`, `uploaded ≥ 1`, `peak ≥ queued`, `frames ≥ 1`).
- Формат `SOS_FRAME_PROFILE` расширен **в конец**; семантика столбцов
  0…24 прежняя.

### Фальсификация

`first_filled` временно писал `uploaded_meshes = 0`. Тест
`simulation_of_sins.startup_profile` немедленно упал
(`empty startup row`), после отката — снова прошёл. Проверка не осталась
декоративной.

Аналогично проверялась чувствительность к «спящему» режиму: при
несфокусированном окне `first_filled` = 427 мс против 17 мс в фокусе, что
подтверждает, что измеряется именно время цикла, а не работа кадра.

## 6. Что отклонено

- **Правки в `game/falling_cubes.c` или `application.c` по производительности
  не вносились.** Все стадии, кроме собственной обвязки кадра, — вызовы
  движка (`RendererCreate`, `RendererBeginFrame`, `RendererEndFrame`,
  физический `VoxelRigidBodyStepEx`). Собственная работа игры при 4000
  телах — 0,12 мс из 13,5 мс (0,86 %); менять нечего.
- **Пре-спавн кубов ради «быстрого» профиля не делался**: он изменил бы
  траекторию кучи и не отражал бы настоящий рост. Профиль снят на реальном
  естественном спавне 100 тел/с.
- **Дерево/сетка и число потоков не перепроверялись**: это уже измерялось в
  [parallel_defaults_parallel_work.md](parallel_defaults_parallel_work.md);
  здесь зафиксировано только то, что профиль клиента идёт с
  `physics_threads=6`, `indexed=0`, `colored`.

## 8. Как повторить

Сборка (Windows MSVC Release):

```powershell
call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat"
cd C:\Users\landi\projects\sos-startup
cmake --preset windows-msvc
cmake --build --preset windows-msvc-release --parallel 4
ctest --preset windows-msvc-release --no-tests=error
```

Стадии запуска (клиент сам закрывается на заполненном кубе):

```powershell
$env:SOS_STARTUP_PROFILE = "$pwd\build\startup.csv"
$env:SOS_NO_VSYNC = '1'
& .\build\windows-msvc\bin\Release\SimulationOfSins.exe
# build\startup.csv: стадии + строка first_filled
```

Профиль кадра без vsync (окно нужно активировать, иначе движок экономит
кадры вне фокуса):

```powershell
$env:SOS_FRAME_PROFILE = "$pwd\build\frame.csv"
$env:SOS_NO_VSYNC = '1'
$env:SOS_PROFILE_SECONDS = '50'
& .\build\windows-msvc\bin\Release\SimulationOfSins.exe
# столбцы: physics_tick_avg_ms, present_avg_ms,
# streaming_avg_ms, instances_avg_ms, streamdraw_avg_ms, between_avg_ms
```

Вспомогательные скрипты замеров (не входят в дерево) сложены в `build/peer/`:
`focus_run.ps1` (запуск с активацией окна), `parse_startup.py`,
`parse_frames.py`.
