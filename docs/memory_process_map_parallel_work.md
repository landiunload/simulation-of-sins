# Карта памяти всего процесса Simulation of sins

Отчёт по задаче «карта памяти всего процесса игры». Измерен устойчивый
процесс целиком: игровая куча, кучи каждого движкового модуля, GPU/рендер,
стеки потоков, образы DLL и неучтённый остаток. Правок в движке нет: игра
получила инструмент `SOS_MEMORY_PROFILE`, а найденное описано как задание
следующей партии. `src/game/*` не менялся (только чтение), формат
`SOS_FRAME_PROFILE`/`SOS_STARTUP_PROFILE` не тронут.

Сырые CSV лежат в `build/peer/A.mem.csv`, `B.mem.csv`, `C.mem.csv`
(и парные `*.frame.csv`). Скрипт разбора — `build/peer/analyze.py`.

## 1. Инструмент: `SOS_MEMORY_PROFILE=<csv>`

Новый модуль [src/app/memory_profile.c](../src/app/memory_profile.c) и
[src/app/memory_profile.h](../src/app/memory_profile.h). Включается
переменной окружения; при выключенном режиме `Create` возвращает `NULL`, а
в кадре остаётся ровно одна проверка указателя. Windows-специфичный код
закрыт `#if defined(_WIN32)`; на прочих платформах — пустые заглушки, так
что модуль собирается и в headless-ядре.

Что делает включённый режим:

- **Перехват куч по IAT.** Сразу после `WindowCreate` (до `RendererCreate` —
  движковые DLL уже загружены статическим импортом) обходятся импортные
  таблицы загруженных `laiue_*.dll` и самой игры и патчатся слоты
  `HeapAlloc`/`HeapFree`/`HeapReAlloc` на хуки. Хук определяет модуль-
  владелец по `_ReturnAddress()` (адрес возврата лежит в вызывающем модуле),
  хранит таблицу указатель→(размер, модуль) и живой/пиковый объём по модулю.
  Таблица — открытая адресация фиксированной ёмкости **1 048 576 записей ×
  16 байт = 16 777 216 байт**, выделена `VirtualAlloc` вне перехватываемых
  куч и намеренно не попадает в собственный учёт (в CSV видна отдельной
  колонкой). Удаление — обратным сдвигом кластера, без надгробий.
  Переполнение — счётчик `heap_lost_allocations`, а не падение.
- **Никаких аллокаций внутри хуков.** Хук сначала вызывает настоящую
  функцию, потом под `SRWLOCK` трогает предвыделенную таблицу; I/O и
  `fprintf_s` делаются уже без замка. Поэтому хуки безопасны для рабочих
  потоков физики и стриминга.
- **Процесс:** `ProcessMemoryCountersEx` (`PrivateUsage`, `WorkingSetSize`,
  `PeakWorkingSetSize`, `PagefileUsage`), `GetProcessHandleCount`, число
  потоков через `CreateToolhelp32Snapshot(TH32CS_SNAPTHREAD)`/`Thread32First`
  по своему PID. Дополнительно по TEB каждого потока
  (`NtQueryInformationThread` + `VirtualQuery`) считается **закоммиченная**
  память стеков; «число потоков × 1 МиБ» идёт отдельной верхней оценкой.
- **Образы:** сумма `SizeOfImage` по всем модулям и отдельно по движковым
  (`EnumProcessModules`-эквивалент через Toolhelp), в байтах.
- **GPU/рендер:** `RendererGetStats` и `ChunkStreamingGetStats` целиком.
- **Остаток:** `PrivateUsage − Σ куч по модулям − GPU-часть, видимая в
  PrivateUsage`. GPU-часть измеряется на старте: `BeginGpuBaseline` до
  `RendererCreate`, `EndGpuBaseline` после `ChunkStreamingCreate`; это
  прирост `PrivateUsage` за вычетом прироста учтённых куч, то есть
  committed-память рендер-стека (UPLOAD-кольца + D3D12/драйвер), которой нет
  в кучах. Отдельной колонкой видно `profiler_table_bytes` — 16 МиБ
  собственной таблицы инструмента, чтобы её можно было вычесть из остатка.

Раз в секунду игрового времени (по времени кадра) пишется строка CSV с меткой
`run`; стадии запуска пишутся метками `window_create`, `content_catalog`,
`renderer_ready`, `world_ready`, `streaming_create`, `run_begin`, в конце —
`final`. Сценарий C добавляет `body_release`/`body_reset`.

Без `SOS_MEMORY_PROFILE` IAT не трогается, `WindowSetMouseLook(..., true)`
как раньше. В замерном режиме окно уводится за пределы экрана
(`SetWindowPos(-32000,-32000)`) и перехват мыши выключается.

## 2. Сценарии

Все прогоны: Windows x64, MSVC Release, `SOS_NO_VSYNC=1`,
`SOS_FRAME_PROFILE` (чтобы работал `SOS_PROFILE_SECONDS`), скрытое за
экраном окно, до 3 потоков сборки. Числа — байты и счётчики, не время.

| сценарий | что делалось | тел в срезе | файл |
| --- | --- | ---: | --- |
| A | старт, устойчивое состояние на плато 300–500 тел | 500 | `A.mem.csv` |
| B | старт, устойчивое состояние до удвоения ёмкости | 3785 (≈4000) | `B.mem.csv` |
| C | старт → ~4000 тел → `SimulationCubeFieldRelease` + `Init` | release 3999 / reset 0 | `C.mem.csv` |

«Устоявшееся» — не менее трёх подряд секунд, где `PrivateUsage` растёт менее
чем на 1 %; у A это 300–500 тел (0 % за 3 секунды), у B — 2100–3785 тел
(рост ~0 % за 16 секунд).

## 5. Сценарий C: сброс поля кубов

Своего ключа сброса тел в игре нет (`SimulationCubeFieldRelease` вызывается
только при выходе). Чтобы сценарий C всё-таки был, в `application.c`
добавлен **замерный** путь `SOS_RESET_BODIES_SECONDS=N`: через N секунд
поле освобождается и заводится заново через публичный API
(`SimulationCubeFieldRelease` + `SimulationCubeFieldInit`), настройки шага
(`executor`, `solverOrder`, `useSpatialIndex`) возвращаются на место.
Без этой переменной поведение не меняется.

| момент | тел | `PrivateUsage`, Б | кучи, Б |
| --- | ---: | ---: | ---: |
| `body_release` (до `Release`) | 3999 | 204 226 560 | 43 438 126 |
| `body_reset` (после `Init`) | 0 | 165 699 584 | 5 130 702 |
| **вернулось** | | **38 526 976** (36.74 МиБ) | **38 307 424** (36.53 МиБ) |

Вернулось ровно то, что держала игра (тел+scratch+кэш+индекс): 38.3 МиБ из
43.4 МиБ живой кучи. GPU-часть (129 МиБ) и прочие модули не изменились —
они с телами не связаны. Дальнейший рост пошёл по той же траектории: за
14 секунд после сброса набралось 1304 тела и 21.9 МиБ куч.

Сырой остаток > 10 % только за счёт **собственной 16-МиБ таблицы

D3D12 после базовой точки. Одной «спрятанной» статьи больше 10 % нет —
это главный отрицательный результат: `VirtualAlloc` мимо куч на устоявшемся
кадре отсутствует, а таблица указателей — цена самого измерения.

## 8. Сверка с прежними отчётами движка

Числа сходятся с отчётами прошлых дней — это одновременно проверка
инструмента и целостности картины:

| статья | отчёт движка | наше измерение | вердикт |
| --- | --- | --- | --- |
| CPU-куча рендера | `memory_render_parallel_work.md`: ~0.03 МиБ | `laiue_render` 35 216 Б (0.034 МиБ) | сходится |
| Таблица стриминга R=2 | `memory_streaming_world_parallel_work.md`: entries 57 344 + scratch 19 208 + drawItems 2 744 + очереди 11 264 ≈ 90 560 Б | `laiue_scene` 91 184 Б | сходится |
| Scratch 4096 тел | `memory_physics_scratch_parallel_work.md`: scratch 31 539 280 Б + кэш 7 340 032 Б + тела 1 114 112 Б + индекс | `simulationofsins` 40 697 998 Б | сходится |
| Лимбы координат | `memory_infinite_coord_parallel_work.md`: 16 000 pile = 2 304 000 Б | `laiue_numeric` 264 480 Б (3785 тел, динамика) | тот же порядок |
| GPU upload-кольца | `memory_render_parallel_work.md`: 40.19 МиБ (кольцо мешей 8 + инстансы 32 + UI 0.19), крупная арена +16 МиБ лениво | внутри `gpu_visible` = 129.13 МиБ | входит |

Отдельно про **DEFAULT против UPLOAD**: отчёт рендера показал перехватом
`CreateCommittedResource`, что committed-ресурсы DEFAULT-кучи в
`PrivateUsage` процесса не входят, а UPLOAD-кольца входят как отображённая
память. Наш замер с этим согласуется: `geometryPoolCapacityBytes` = 4 МиБ
(и это при `used ≈ 672` Б), тогда как 40 МиБ колец действительно видны в
PrivateUsage наравне с драйверными ~85 МиБ. Мы **не** повторяли перехват
`CreateCommittedResource` (это уже сделано в отчёте рендера) — здесь
проверена совместимость числа в контексте целого процесса: движковых
GPU-ресурсов ~40 МиБ, всё остальное из 129 МиБ — рантайм D3D12 и драйвер.

## 9. Три крупнейших потребителя

1. **Рендер-стек D3D12 — `gpu_visible` 135.4 МиБ (66–80 % PrivateUsage).**
   В устойчивом состоянии **нужен**: без committed-ресурсов и рантайма кадра
   нет. Из них движковых, по `memory_render`, ~40 МиБ (UPLOAD-кольца,
   крупная арена лениво), DEFAULT-пул 4 МиБ, остальные ~85 МиБ —
   рантайм/драйвер D3D12, на которые игра и движок не влияют. Единственная
   крупная управляемая статья — фиксированное инстансное кольцо 32 МиБ
   (16 МиБ × 2 слота кадра); `memory_render` уже разбирал его и отклонил
   уменьшение как смену публичного контракта «сколько инстансов кадр может
   нарисовать без потерь».
2. **Игровые буферы шага — `simulationofsins` 38.8 МиБ (19.8 % на B).**
   Нужны, пока живы тела: `VoxelRigidBody[]`, `scratch`, кэш контактов,
   broadphase. Совпадает с `memory_physics_scratch`. Замечание для
   следующей партии: игра растит их **под `capacity`, а не под `count`**
   ([src/game/falling_cubes.c](../src/game/falling_cubes.c), `GrowTo`, и
   вызов `GrowTo(field, field->capacity * 2u)` в спавне). Сразу после
   удвоения зарезервировано до ~2× нужного: например, при 2100 телах
   ёмкость 4096, и 41.3 МиБ живут там, где хватило бы ~21 МиБ. Это не
   утечка, а амортизированное удвоение; уменьшает потери рост с меньшим
   коэффициентом (например 1.5×) отдельно для буферов шага. Правка — в
   игре, не в движке; по условию задачи `src/game/*` не менялся.
3. **Всё прочее: `laiue_mesher` 2.22 МиБ + остальные кучи движка (Σ 0.38 МиБ
   без mesher) + остаток 8.63 МиБ (4.4 %).** `laiue_mesher` — рабочие буферы
   сборки мешей, **нужны** в устоявшемся кадре (125 чанков обзора).
   Остаток без таблицы профилировщика < 10 %: это стеки (0.35 МиБ), кучи
   CRT, приватные страницы образов и поздний рост D3D12. Скрытой крупной
   статьи нет.

## 10. Указания для правок движка (задание следующей партии)

1. **`src/render/renderer.h`, `RendererStats`** — добавить байты
   committed/upload-памяти рендера (resident bytes колец, крупной арены,
   DEFAULT-пула и текстур). Сейчас публично виден только
   `geometryPoolUsed/CapacityBytes`, поэтому GPU-часть процесса приходится
   оценивать косвенно. Заполнять в `src/render/renderer_d3d12.c` там, где
   создаются буферы (`CreateMeshUploadBuffers`,
   `EnsureLargeMeshUploadBuffer`) и ресурсы (`CreateCommittedResource`).
   Без этого честный остаток `PrivateUsage − кучи − GPU` неполон.
2. **`src/scene/chunk_streaming.h`, `ChunkStreamingStats`** — добавить
   `residentBytes` (entries + rebuild-арена + drawItems + очереди). Это
   91 КБ на R=2, но с ростом радиуса обзора растёт как `(2R+1)³`; сейчас
   видно только счётчики, а не память.
3. **`src/render/renderer_d3d12.c`, инстансное кольцо** — 32 МиБ
   (`MESH_UPLOAD_BYTES_PER_FRAME`/`instance`-кольцо, 16 МиБ × 2 слота) —
   крупнейшая фиксированная управляемая статья. `memory_render` уже
   рассмотрел и отклонил ленивое создание; в целой картине процесса это
   ~16–20 % PrivateUsage, поэтому предложение стоит пересмотреть в мажорной
   версии (ленивое/адаптивное кольцо с сохранением контракта «не терять
   вызовы молча»).
4. **`src/numeric/` (лимб `InfiniteCoord`)** — `memory_infinite_coord`
   предлагал инлайн однолимбового значения в поле `limbs`; на 4000 тел это
   ~0.5 МиБ, меньше процента процесса. Не приоритет; менять только вместе с
   мажорным ABI.
5. **Не менять** `src/platform/system_windows.c` (`PlatformAllocate` →
   `HeapAlloc(GetProcessHeap())`) и `src/platform/window.c`: прямой
   `HeapAlloc` — как раз то, что делает возможным IAT-учёт по модулям без
   правок движка.

## 11. Ограничения

- Только Windows x64, MSVC Release (сборка и clang-tidy-зеркало —
  `windows-clang`). Linux/macOS/ARM64 и Debug не гонялись: код
  Windows-специфичен и в тех профилях превращается в заглушки.
- `gpu_visible` — производная величина: прирост `PrivateUsage` на отрезке
  `RendererCreate`…`ChunkStreamingCreate` минус прирост куч. Она не
  разделяет UPLOAD-кольца, swapchain, рантайм и драйвер; разделение взято из
  `memory_render`. Прямой перехват `CreateCommittedResource` не повторялся.
- `PrivateUsage` шумит на общей машине (аллокатор, драйвер): между прогонами
  `gpu_visible` гуляет на ~1–3 МиБ из 129 МиБ. Для вычетов использовались
  байты внутри одного прогона, а не вычитание между запусками.
- Стеки считаются точно по TEB через `NtQueryInformationThread`: на 29–30
  потоках закоммичено 0.33–0.36 МиБ, тогда как верхняя оценка «потоки ×
  1 МиБ» даёт ~30 МиБ зарезервированного (но не закоммиченного).
- Число потоков 29–30 включает рабочих физики/стриминга и потоки D3D12;
  пофайловая разбивка потоков не снималась.
- Аллокации, сделанные движком до установки хуков (`WindowCreate`,
  `InputCreate`, `ContentCatalogCreate`), в Σ куч не входят и сидят в
  остатке. Их вклад мал (к `content_catalog` кучи всего 468 Б), и именно
  поэтому хуки ставятся сразу после окна.

## 12. Как повторить

```bat
call "C:\Program Files\Microsoft Visual Studio\2022\Community\VC\Auxiliary\Build\vcvars64.bat"
cd /d C:\Users\landi\projects\sos-memtotal
cmake --preset windows-msvc
cmake --build --preset windows-msvc-release --parallel 3

build\peer\run_profile.bat A 6
build\peer\run_profile.bat B 40

build\peer\run_profile.bat C 54

python build\peer\analyze.py build\peer\A.mem.csv build\peer\B.mem.csv build\peer\C.mem.csv
```

Прямой эквивалент без вспомогательного `.bat` (из
`build\windows-msvc\bin\Release`, где лежат ассеты):

```bat
set SOS_NO_VSYNC=1
set SOS_PROFILE_SECONDS=6
set SOS_FRAME_PROFILE=%CD%\..\..\peer\A.frame.csv
set SOS_MEMORY_PROFILE=%CD%\..\..\peer\A.mem.csv
SimulationOfSins.exe
```

`SOS_FRAME_PROFILE` нужен только потому, что ограничение `SOS_PROFILE_SECONDS`
живёт в кадровом профиле; `SOS_MEMORY_PROFILE` его не трогает. Окно уводится
за экран самим профилировщиком. `analyze.py` — простой разбор CSV по
колонкам, он не обязателен и приведён для удобства.

## 13. Проверка и обязательные свойства

- **Сборка MSVC Release** без предупреждений (`/W4 /WX`), границы модулей
  `OK (105 files)`.
- **CTest windows-msvc-release — 9/9**, включая `startup_profile`, `render`,
  `rebase_render`, физические `physics_overrides`/`physics_defaults`.
